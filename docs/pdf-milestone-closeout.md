# PDF milestone closeout map

## PDF library target (October 2026)

New PDFsharp/MigraDoc patches target the independent MIT-based
[`Pdfxport.Net`](https://github.com/gaspardpetit/Pdfxport.Net) fork, not
PDFsharp releases after 7.0.0 Preview 1. Review the existing isolated
candidate branches against the fork's `main` before carrying any patch
forward; do not mix the AGPL/commercial upstream line into the composed
source stack. The fork publishes `Pdfxport.Net` and
`Pdfxport.Net.MigraDoc` packages while retaining the `PdfSharp` and
`MigraDoc` namespaces. The fork's `main` is eight commits ahead of the
current `ext/PDFsharp` checkout, which is its direct ancestor. The
`.gitmodules` URL now targets the fork, but the submodule checkout has
uncommitted changes and has not been advanced. Package-reference migration
remains separate work. The fork already includes the independent
prepend-content duplicate fix (`d34086a`, merged as `4740259`), so its
older local candidate must not be submitted again. The existing submission
order below was written for the earlier `origin/master`; recheck each
unmerged candidate against the fork's `main` before preparing a PR.

## Milestone acceptance rule

Use Word as the reference. For each document, accept the PDF visual
result when its smoothed Word RMSE is at most 0.010 **or** its smoothed
Word RMSE is lower than Aspose 25.8's against the same Word reference.
Compare the same document and pages with the same raster/scoring settings;
do not compare flow-to-Aspose directly. Correct Word pagination, successful
export, and required content remain independent gates. An Aspose win does
not excuse a missing page or missing feature. Aspose has now been
rescored against the current Word references for every document above
0.010; the promoted export passes this visual/pagination/export gate,
but its remaining feature/content gates still need verification before
milestone sign-off.
The PDF exporter's `net8.0` target builds with the composed PDFsharp 7
source. The full multi-target package build is not currently green:
`netstandard2.0` first reports a default-interface implementation and
`IReadOnlySet` incompatibility; a diagnostic compatibility-only change
exposed 712 further framework API errors (including `Math.Clamp` and
`IReadOnlyDictionary.GetValueOrDefault`). That partial change was
reverted. Multi-target support needs a separate deliberate port or
target-framework decision; do not claim release-build readiness from
the passing `net8.0` build alone.
